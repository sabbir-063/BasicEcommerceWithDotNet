# 12 - Testing Strategy

## Testing pyramid
Use a mix of:
- unit tests for domain/business rules;
- integration tests for real API + PostgreSQL behavior;
- frontend component tests for critical rendering/forms;
- Playwright/browser E2E for core journeys;
- real development-service smoke tests for Neon and Cloudinary.

Do not use the development Neon database as the only automated test database. Automated tests must remain repeatable and should not destroy development data.

## Backend unit tests
Prioritize pure rules:
- order status transition matrix;
- line/total calculations;
- slug helper if custom;
- cancellation eligibility;
- validation helpers;
- authorization/ownership service logic where isolated.

## Backend integration tests
Prefer a disposable PostgreSQL Testcontainer so behavior matches PostgreSQL rather than an in-memory EF provider.

Test real HTTP endpoints using `WebApplicationFactory` or equivalent.

Required scenarios:

### Auth
- register success;
- duplicate email conflict;
- bad login rejected;
- customer cannot access admin route;
- admin can access admin route;
- inactive user login rejected.

### Categories/products
- active filtering;
- product pagination;
- search;
- category filter;
- create/update/disable authorization;
- invalid price/stock rejected.

### Cart
- new cart created;
- add item;
- add same item upserts quantity;
- update quantity;
- reject above stock;
- remove item;
- another user cannot mutate item by guessed ID.

### Checkout
- rejects empty cart;
- uses server price, not client value;
- creates order snapshots;
- decrements stock;
- clears cart;
- rollback on insufficient stock;
- stock never negative under concurrent purchase attempt.

### Cancellation
- Pending customer cancel succeeds;
- stock restored;
- double cancellation does not double restore;
- other user's order cannot be cancelled;
- Shipped/Delivered cannot be cancelled.

### Admin order workflow
- valid transitions succeed;
- invalid transitions conflict.

## Frontend unit/component tests
Cover high-risk UI logic, not every class name.

Examples:
- currency formatter;
- API Problem Details parsing;
- login validation;
- cart row quantity bounds;
- checkout submit disables while pending;
- status action rendering for customer/admin;
- protected route behavior.

Mock network at component level only where appropriate. E2E covers real integration.

## Playwright E2E
Use dedicated E2E test user/admin and deterministic seed data.

Minimum specs:
1. public catalog browse/search/filter;
2. register/login/profile/logout;
3. admin product create with image workflow can be separate smoke test if live Cloudinary makes normal E2E expensive;
4. add/update/remove cart;
5. COD checkout;
6. customer order view/cancel;
7. admin order progression;
8. authorization redirect/403 UX.

## Browser-agent manual verification
Because Codex can use a browser, after each vertical feature it should also manually verify the actual running site, especially before the full E2E suite exists.

Check:
- visible UI result;
- console errors;
- failed requests;
- status codes;
- request/response shape excluding secrets;
- responsive layout.

## Real Neon development smoke tests
After migration and major DB features:
- call `/health/ready`;
- create/read a harmless dev entity or use seeded data;
- verify migrations table/version;
- run one complete checkout flow in dev data;
- clean only data specifically created for the smoke test when safe.

Never run test database wipe against the owner-provided Neon URL unless the database is explicitly designated disposable.

## Real Cloudinary smoke tests
- upload a dedicated small test image;
- verify returned secure URL loads;
- verify public ID folder;
- delete test image if not retained as seed asset.

## Test data isolation
Use unique emails/order markers for automated runs, e.g. timestamp/random suffix generated by test code. Do not hard-code a single mutable customer across parallel tests unless test reset is deterministic.

## Commands expected in final README
Backend:
```text
dotnet test
```

Frontend:
```text
npm run lint
npm run typecheck
npm test
npm run build
npm run e2e
```

Exact scripts must exist before project is considered done.

## Failure policy
A failed test is not silently skipped. Codex must:
1. diagnose;
2. fix product code/test setup;
3. rerun relevant tests;
4. record any intentionally skipped test with reason in implementation status.
